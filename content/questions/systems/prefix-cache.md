## 从问题出发

多个请求重复发送长文档，每次都 prefill 很浪费。Prefix cache 复用已计算的前缀 K/V；与当前请求内部的 [KV cache](#q=kv-cache) 相联系，但额外处理跨请求复用。

## 什么情况下可以复用？

同一模型和兼容配置下，因果 decoder 中相同 token 前缀会产生相同前缀 K/V。若早期 token 改变，后面即使文本相同，其 K/V 也可能因上下文不同而改变。

缓存实现通常还需要区分模型/adapter、相关输入或配置，并处理块粒度与隔离。实际 key 包含哪些额外字段，应查服务框架版本，不能把“文本一样”作为完整正确性条件。

## 为什么命中失败？

- chat template、空格或特殊 token 导致前缀 token 不一致。
- 在开头加入时间戳或每次改变工具描述，破坏长共享前缀。
- 压缩/重写历史改变早期内容。
- KV 块被内存压力驱逐，或请求到了无对应缓存的 worker。
- 共享前缀短于有效块粒度，实际可复用范围有限。

把稳定资料放前、动态问题放后是常见设计办法，但应首先保证信息布局合理，不能为了命中率损伤任务理解。

## 能加速什么，不能加速什么？

主要跳过共享部分的 prefill 计算；生成新 token 的 decode 仍需执行。文档很长而回答很短时较容易体现收益；输出很长时端到端比例收益可能被 decode 稀释。

以下示意并非任何系统固定耗时：若 80% 时间是可复用 prefill，剩余 20% 为 decode 等，完全消除该 prefill 的理想上限是 5 倍；现实还有限定和缓存开销。

## 小实验与自检

在明确版本的服务上发送“相同长前缀+不同短后缀”，区分冷/热缓存测 TTFT；再修改前缀第一个 token 和后缀，观察差别。报告命中统计、路由和并发条件。

自检：缓存命中为何不意味着整次请求无需模型计算？多轮摘要为何可能损害复用？
