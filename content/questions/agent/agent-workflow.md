## 从问题出发

模型调用了搜索 API，就一定是 Agent 吗？比名字更重要的是：谁决定下一步，以及系统如何确认完成。

## 从决策权区分

固定代码规定“检索 → 总结 → 格式化”是 workflow；模型依据当前观察决定“搜索什么、调用哪个工具、是否继续”属于更自主的 Agent 模式。实际系统可以混合：外层状态机限制步骤，内层模型选择行动。

下面是本文的设计示例，不是声称你已有的项目：

| 场景 | 优先考虑 | 原因 |
|---|---|---|
| 从固定字段生成报告 | 单次调用或固定流程 | 输入输出和路径明确 |
| 需要两次资料核验 | 小型 workflow | 易记录每步证据 |
| 调试未知代码错误 | 受限 Agent 循环 | 下一步依赖运行反馈 |

## 一个最小闭环

```text
目标与约束 → 构造上下文 → 模型提出 action
                              ↓
                       校验参数并执行工具
                              ↓
                       observation 与状态更新
                              ↓
                  结束验证 / 继续 / 达到预算上限
```

结束不能只依赖模型说“完成”。例如代码任务可用测试与差异检查，研究任务可检查来源与问题覆盖；预算限制也要返回未完成状态而非冒充成功。

## 为什么先做简单 baseline？

更长循环意味着更多延迟、成本和出错机会。若单次回答已经足够，多步没有必然收益。比较时固定任务集和资源预算，用成功率改善证明复杂度值得，而非凭架构图判断。

## 小实验与自检

给一个公开资料调研任务设计三种方案：单次回答、固定检索流程、工具循环。列出每种方案的失败方式和完成判据。先用 10 个任务手工归因，再决定是否增加自治。

自检：模型能选工具但不能改流程算什么？回答时说明控制权的具体范围即可，不必争标签。
