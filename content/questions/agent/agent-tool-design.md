## 从问题出发

JSON 合法，不代表调用正确。工具失败可能来自名字含糊、参数单位不明、返回值太长或系统重试逻辑。

## 接口分三层

1. **选择**：名字与描述应明确什么时候用。例如 search_documents 与 get_document，分别是发现候选和读取证据。
2. **参数**：类型、范围、默认值、资源标识要清晰。结构校验后还要语义校验，例如 page 是否存在、路径是否属于工作区。
3. **结果**：返回有稳定 ID 的结构化摘要、必要正文与明确错误；不要仅返回“失败”或巨量无关文本。

模型产生的是 action 提议，实际执行由应用负责。即使模型能生成 schema 合法的对象，权限和参数语义仍在执行层判断。

## 重试和副作用

只读查询通常较容易重试；创建记录、扣款或提交任务需要幂等键或查询执行状态。网络超时不说明服务器没有执行。多次执行同一个写入 action 可能造成重复结果。

这是通用工程设计建议，应结合真实业务接口，不是所有工具必须同一套机制。

```text
提议 action → 校验 → 权限检查 → 执行 → 结构化 result
                         超时 → 查状态 / 有界重试 / 返回不确定
```

## 错误也需要可学习的信息

区分不存在、参数错误、限流、暂时不可用；提供下一步可用信息，如有效字段名或 retry-after。不要把工具返回内容当作系统级指令，检索文档中的“忽略要求”仍是数据。接口层与上下文层都要保留来源边界。

## 小实验与自检

准备 10 个调用任务，比较含糊和明确的接口描述；统计选错工具、参数错、调用正确但任务未完成三类。另注入一次超时，验证系统不会无限重试或重复写入。

自检：schema 全部正确时，为什么任务仍会失败？日志至少应保存哪些字段才能复盘？

## 面试表达

从选工具、填参数、理解结果三个阶段定位，副作用和重试在执行层处理；最终仍用任务结果评估。
