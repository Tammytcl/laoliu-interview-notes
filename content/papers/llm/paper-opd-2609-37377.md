## 1. 背景与已有工作

**阅读定位。**《Beyond Prompt Count: How Data Shapes Transfer in On-Policy Distillation》放在 OPD 文献链条中，核心问题不是把一个最终答案从 teacher 复制给 student，而是 student 先在当前策略下生成前缀，teacher 再对这些真实会遇到的状态提供监督。这样可减少离线 teacher 轨迹与 student 部署轨迹的分布偏移，但代价是每轮都要生成、teacher 前向和更新，稳定性、概率空间以及评测预算会互相耦合。

本报告把贡献拆成“问题假设—训练信号—工程实现—证据边界”四层。与 SFT 相比，OPD 监督的是 student rollout；与 RL 相比，它通常不必为每题设计外部 reward，而以 teacher 分布或似然差为反馈；与离线 KD 相比，它能在 student 的错误前缀上纠偏。若 teacher 与 student tokenizer、终止符或能力分布不同，还会额外出现概率不可比、长度偏差或局部信号失真的问题。阅读原文时应先确认论文解决的是哪一层，而不是把所有提升笼统归因于“on-policy”。

这套定位也限定了结论：论文中的 benchmark 增益只能支持给定模型、数据和预算下的机制，不能自动外推到任意规模或任务。尤其需要区分 teacher 更强带来的上限、训练 token 更多带来的算力收益，以及新目标函数本身的贡献。后文保留原论文图表证据与负结果，避免只摘摘要中的最佳数字。

传统直觉认为，后训练数据越多、来源越杂，OPD 越能泛化。这篇研究固定 student/teacher 与总 rollout 数，系统减少**不同 prompt 的数量**，观察有些设置只需很少题仍能提升，有些设置则对 prompt 选择极敏感。它把“有多少独特题目”与“同一题重复生成多少轨迹”拆开，是理解 on-policy 数据效率的重要实验。

多教师能力整合还涉及 prompt 来源偏好：数学题不一定最能让 student 从数学 teacher 学到一般推理能力，代码题可能刺激更有用的决策点。不能用数据集名称直接推断蒸馏信号价值。

## 2. 方法与实现机制

![Table 1：教师—学生对与 OPD 数据来源](./assets/papers/paper-opd-2609-37377/study-pairs-pdf.png)

这是一项数据支持集研究，原表比结果概览图更适合说明实验设计。表中区分自训练教师、公开 checkpoint、同尺寸与跨尺寸配对，并给出每组的 prompt 来源；后续数据数量和选择策略的实验都依赖这些条件。不同模型对不可互换，prompt efficiency 也不意味着任意 prompt 都能达到同样效果。 图表源：[arXiv 2609.37377v1 PDF，第 3 页](https://arxiv.org/pdf/2609.37377v1#page=3)，仅裁图表区域。

作为比较基线，student 轨迹记为 $y\sim\pi_\theta(\cdot\mid x)$，teacher 为 $\pi_T$。常见 token 级 on-policy 蒸馏的示意目标写成下式；它不代表本文所有变体都采用同一散度或同一梯度估计器：

$$\mathcal{L}(\theta)=\mathbb{E}_{x,\,y\sim\pi_\theta(\cdot\mid x)}\!\left[\sum_t D\!\left(\pi_\theta(\cdot\mid x,y_{<t}),\pi_T(\cdot\mid x,y_{<t})\right)\right].$$

这里最关键的是期望分布也依赖 student：参数更新后，下一批前缀会变，teacher 监督的位置随之移动。若实现先缓存 teacher 自己生成的固定答案，目标就退化为 off-policy；若 teacher 和 student 看到的模板、温度或 EOS 不一致，似然差还会混入协议偏差。散度是 reverse KL、forward KL、JS、回归损失还是经过门控的组合，会决定 mode-seeking、coverage 和梯度尺度，不能只用“KD loss”概括。

复现时建议把一次训练 step 拆成六个可审计阶段：固定 prompt 与模板；student 生成并记录 token/终止原因；teacher 在完全相同前缀上前向；构造论文定义的 token 掩码、权重或对齐；只对 student 反向；记录有效 token 数与梯度范数。对于跨 tokenizer 方法，还必须保存共同 byte/event 单元到两侧 token 的映射；对于自蒸馏，必须冻结 teacher 快照或明确同步频率；对于 verifier/多 teacher 方法，则要记录门控拒绝率与各 teacher 被选比例。

公式实现有三个常见陷阱。第一，用 batch mean 代替有效 token mean 会让长回答获得更大权重；第二，teacher logits 的温度缩放、top-k 截断和重新归一化次序会改变目标；第三，在本应 stop-gradient 的权重上反传，会引入论文没有的高方差项。最小测试应构造一个两 token 词表，手算每项概率、mask 与梯度方向，再做端到端小 batch 对照。作者未开源与该论文一一对应的官方代码仓库，因此这里只能依据固定版论文、公式和附录核读，不能声称函数级实现已验证。

方法是否有效不能只看最终 accuracy。还要检查训练中 teacher-student KL、student 熵、回答长度、EOS 概率、有效更新 token 比例、梯度范数和 rollout 成功率。若主指标上涨却长度暴增、熵坍缩或 OOD 明显下降，应视为带代价的权衡。原文方法图、后续配置说明和结果图表共同构成可追溯链条。

作者把训练 prompt 支持集固定为 $M$ 个不同样本，student 在这些 prompt 上持续采样新 rollout；teacher 在每次新前缀评分，反向优化仍按 sampled-token reverse-KL 风格进行。这里“只用 1 题”不是重复训练同一个固定答案：每轮 student 的生成分布变化，trajectory 也更新。因而它考察的是 prompt 多样性的下限，而非否认轨迹多样性的作用。

第二层实验比较不同来源：DeepMath、DAPO、代码、IF、Agent 等，控制 prompt 数与部分 token 预算，并在数学、GPQA、代码、指令和工具调用上评估迁移。Table 2 特别控制总训练 token，防止“DeepMath 更好只是答案更长”。原文没有确认到作者专门训练仓库；open-r1 链接是被引基础设施，不应冒充方法代码。

## 3. 实验设置与算力

![Table 10：OPD 超参数](./assets/papers/paper-opd-2609-37377/table-10-config-pdf.png)

这里只裁取 Table 10，不包含同页 Math RL、Code RL 和 SFT 的其他配置。OPD 采用何种 rollout 数、batch、长度和目标函数应按本表读取，训练 step 还由具体模型对决定。把邻近教师训练表的参数抄到蒸馏配置中，会让复现改变问题本身。 图表源：[arXiv 2609.37377v1 PDF，第 17 页](https://arxiv.org/pdf/2609.37377v1#page=17)，仅裁图表区域。

| 复现维度 | 必须记录的字段 | 为什么重要 |
|---|---|---|
| 模型协议 | checkpoint、tokenizer、chat template、EOS | 决定概率是否可比 |
| 采样预算 | prompts、每题 rollout、温度、top-p、最大长度 | 决定探索与成本 |
| 优化 | loss、学习率、batch、累积、step/epoch | 决定梯度尺度 |
| teacher 成本 | 前向 token、logits/top-k、缓存策略 | OPD 的主要额外开销 |
| 评测 | seed、样本数、Avg@k/Pass@k、judge | 防止口径漂移 |
| 算力 | GPU 型号、卡数、GPU-hours | 判断收益是否等预算 |

公平对照至少要固定 student 起点、训练 prompt、生成 token 总量和评测解码。只固定 step 不够：多 rollout、更长回答和更大 teacher 会显著增加计算。若论文没有完整 GPU 型号、卡数或 GPU-hours，本报告将其视作披露缺口；复现时需单独测量 student 生成、teacher 前向、反向传播和评测四部分 wall-clock。已有正文中的论文专属模型、数据和参数说明应与这张账本结合阅读。

统计上应报告多个随机种子或置信区间，并把 checkpoint 选择放在独立验证集。Pass@k 会随 k 和采样温度上涨，不能与 greedy accuracy 混写；LLM judge 需要固定版本与 prompt；verifier 过滤后的有效样本量也要报告。只有配置、预算和指标都对齐，结果差异才可归因于方法。

实验跨数学 RL continuation、代码 RL continuation、30B Instruct→4B/1.7B 与 1.5B 推理模型。$M$ 从 1、8、48 到数千，固定或比较 rollout 总数；评测包含数学、GPQA-D、HumanEval+、LiveCodeBench v6、IFEval、IFBench、BFCL-v3。某些表报告 mean@8 或 mean@16，需按表头读。

少 prompt 反复 rollout 可能降低数据收集成本，却不一定减少 teacher/student 前向 token；“少题”与“省 GPU”不是同义词。主文未给统一 GPU-hours；应分别记录 prompt 去重数、rollout 数、生成 token 与 optimizer steps。

## 4. 结果与图表解读

![Table 3：多领域教师下的数据来源偏好](./assets/papers/paper-opd-2609-37377/table-3-results-pdf.png)

原表固定 Qwen3-4B 多领域 RL 教师与对应学生、支持集规模 M=48，比较不同来源的 prompt 在多个领域上的影响。它隔离了数据组成而非数据量，揭示某个领域更合适的支持集未必在其他领域同样占优。不能据单个领域分数高就判断该选择器具有普适优势。 图表源：[arXiv 2609.37377v1 PDF，第 6 页](https://arxiv.org/pdf/2609.37377v1#page=6)，仅裁图表区域。

![Figure 4：参数位移与功能对齐](./assets/papers/paper-opd-2609-37377/functional-alignment-source.png)

原图对照参数空间余弦和多个领域上的功能变化，追踪不同 checkpoint 相对教师方向的移动。参数更接近教师不必然意味着所有任务表现都更接近教师，因为训练 prompt 决定了被激活和强化的功能子空间。这里的关联支持分析数据选择的作用，但不构成参数相似度对能力提升的充分条件。 图源：[arXiv 2609.37377v1 LaTeX 源码](https://arxiv.org/src/2609.37377v1)，原始文件 `figures/fig4_functional_changes.pdf`。

结果证据应形成闭环：主表回答“最终是否更好”，曲线回答“训练是否更稳/更快”，消融回答“哪个部件起作用”，成本表回答“是否等预算”。任一环节缺失都降低因果强度。尤其在 OPD 中，更强 teacher、更长 rollout 或更多 teacher 前向本身就可能提高分数，因此必须同时报告 teacher 调用量和生成 token。只引用平均值还会掩盖 AIME 这类小样本基准的高方差。

实践决策不能只追最高 accuracy。若目标是单次在线回答，应重视 Pass@1/Avg@k 与延迟；若允许 test-time scaling，才关注较大 k 的 Pass@k；若模型需要持续更新，还要测 OOD、遗忘和连续多轮蒸馏。本文据原图与正文只给“这些实验设置下”的结论，不把局部结果外推成普遍规律。

正文的极端例子：Qwen3-4B Math-RL 设置，在总共 **3,840** 条 rollout 匹配时，只用 1 个 prompt 的数学分数 **44.74**，使用 3,840 个 prompt 为 **46.77**。Code-RL 设置中 **48** 个 prompt 在 step 100 与 **22,618** 个 prompt 全池结果只差约 **0.10**；但作者也展示单 prompt 代码运行的结果从 **50.03 到 61.37**，跨度很大，说明选题比数量更关键。

**Table 2** 固定 $M=48$ 并把 GSM8K 的训练 token 从 **1.19M** 补到 **16.14M**，四项均分只从 **44.01** 到 **44.84**；DeepMath **16.63M token** 得 **51.02**。这支持“数据来源与内容质量”不能全由 token 数解释。**Table 3** 中多域 teacher 的 Eurus Code 来源 Avg6 **57.63**，DeepMath **54.65**，IF **48.67**；不同来源对非本域能力的迁移方向也不一样。

## 5. 局限、结论与后续阅读

共同局限可以归为四类：teacher 可能在 student 前缀上失准；on-policy 反复调用 teacher，训练成本高于离线 SFT；tokenizer/EOS/template 不一致会把协议差异伪装成知识差异；多数论文集中在数学或可验证任务，开放式对话、代码和长期遗忘证据仍少。Beyond Prompt Count: How Data Shapes Transfer in On-Policy Distillation 应在这些边界内理解，不能因一个平均分提升就宣称普遍优于所有蒸馏或 RL 方法。

后续复现优先做等生成 token、等 teacher 前向和等 GPU-hours 三套对照，并报告长度、熵、KL、有效 token、梯度范数、OOD 与失败案例。阅读路线可依次对照普通 off-policy KD、标准 RKL OPD、本文专属改进以及同主题的稳定化/跨 tokenizer 工作。最终判断标准是“收益来自哪里、付出什么成本、在何种条件下失效”，而不是只复述摘要。

少 prompt 得分接近全池，并不意味着任意单题都可以；论文自己给了大量选择敏感性的反例。若设计日常 OPD 训练数据，应先做小规模 source ablation，再扩大样本数，且关注与预期部署任务的 transfer。该研究使用特定 teacher/student 和评测集合，不能推广成“OPD 不需要数据多样性”的口号。
