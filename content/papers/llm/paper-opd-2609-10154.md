## 1. 背景与已有工作

**阅读定位。**《CompassOPD: Cross-Family On-Policy Distillation via Within-Family Likelihood Shifts》放在 OPD 文献链条中，核心问题不是把一个最终答案从 teacher 复制给 student，而是 student 先在当前策略下生成前缀，teacher 再对这些真实会遇到的状态提供监督。这样可减少离线 teacher 轨迹与 student 部署轨迹的分布偏移，但代价是每轮都要生成、teacher 前向和更新，稳定性、概率空间以及评测预算会互相耦合。

本报告把贡献拆成“问题假设—训练信号—工程实现—证据边界”四层。与 SFT 相比，OPD 监督的是 student rollout；与 RL 相比，它通常不必为每题设计外部 reward，而以 teacher 分布或似然差为反馈；与离线 KD 相比，它能在 student 的错误前缀上纠偏。若 teacher 与 student tokenizer、终止符或能力分布不同，还会额外出现概率不可比、长度偏差或局部信号失真的问题。阅读原文时应先确认论文解决的是哪一层，而不是把所有提升笼统归因于“on-policy”。

这套定位也限定了结论：论文中的 benchmark 增益只能支持给定模型、数据和预算下的机制，不能自动外推到任意规模或任务。尤其需要区分 teacher 更强带来的上限、训练 token 更多带来的算力收益，以及新目标函数本身的贡献。后文保留原论文图表证据与负结果，避免只摘摘要中的最佳数字。

不同模型家族之间做 OPD，teacher 与 student 的语言习惯、tokenizer 和基础分布都可能不同。直接用强 teacher 对 student token 的 log-prob 差，既包含真正的能力增益，也包含整个模型家族的先天概率偏移。CompassOPD 想从师生差中隔离**强 teacher 相对同家族弱参考模型究竟学到了什么**，再把这个变化迁给 student。

它与 [SimCT](#paper=paper-opd-2605-07711) 一样要处理文本事件对齐，但重点不同：SimCT 构造共同监督单位；CompassOPD 增加 teacher 家族内部参照与 student 起点参照，避免“跨家族偏移”被误当奖励。

## 2. 方法与实现机制

![CompassOPD 的教师—参考模型校正](./assets/papers/paper-opd-2609-10154/method-source.png)

原图让强教师及同族参考模型对同一对齐文本动作评分，利用二者的似然差减去模型族偏置，再以学生侧信号校准更新。这里多出的参考模型不是另一个独立答案来源；它提供用于区分能力信号与 tokenizer/家族偏好的基准。实现必须保持三方评分的文本边界一致。 图源：[arXiv 2609.10154v1 LaTeX 源码](https://arxiv.org/src/2609.10154v1)，原始文件 `figs/compassopd_method.pdf`。

作为比较基线，student 轨迹记为 $y\sim\pi_\theta(\cdot\mid x)$，teacher 为 $\pi_T$。常见 token 级 on-policy 蒸馏的示意目标写成下式；它不代表本文所有变体都采用同一散度或同一梯度估计器：

$$\mathcal{L}(\theta)=\mathbb{E}_{x,\,y\sim\pi_\theta(\cdot\mid x)}\!\left[\sum_t D\!\left(\pi_\theta(\cdot\mid x,y_{<t}),\pi_T(\cdot\mid x,y_{<t})\right)\right].$$

这里最关键的是期望分布也依赖 student：参数更新后，下一批前缀会变，teacher 监督的位置随之移动。若实现先缓存 teacher 自己生成的固定答案，目标就退化为 off-policy；若 teacher 和 student 看到的模板、温度或 EOS 不一致，似然差还会混入协议偏差。散度是 reverse KL、forward KL、JS、回归损失还是经过门控的组合，会决定 mode-seeking、coverage 和梯度尺度，不能只用“KD loss”概括。

复现时建议把一次训练 step 拆成六个可审计阶段：固定 prompt 与模板；student 生成并记录 token/终止原因；teacher 在完全相同前缀上前向；构造论文定义的 token 掩码、权重或对齐；只对 student 反向；记录有效 token 数与梯度范数。对于跨 tokenizer 方法，还必须保存共同 byte/event 单元到两侧 token 的映射；对于自蒸馏，必须冻结 teacher 快照或明确同步频率；对于 verifier/多 teacher 方法，则要记录门控拒绝率与各 teacher 被选比例。

公式实现有三个常见陷阱。第一，用 batch mean 代替有效 token mean 会让长回答获得更大权重；第二，teacher logits 的温度缩放、top-k 截断和重新归一化次序会改变目标；第三，在本应 stop-gradient 的权重上反传，会引入论文没有的高方差项。最小测试应构造一个两 token 词表，手算每项概率、mask 与梯度方向，再做端到端小 batch 对照。作者未开源与该论文一一对应的官方代码仓库，因此这里只能依据固定版论文、公式和附录核读，不能声称函数级实现已验证。

方法是否有效不能只看最终 accuracy。还要检查训练中 teacher-student KL、student 熵、回答长度、EOS 概率、有效更新 token 比例、梯度范数和 rollout 成功率。若主指标上涨却长度暴增、熵坍缩或 OOD 明显下降，应视为带代价的权衡。原文方法图、后续配置说明和结果图表共同构成可追溯链条。

同一 student rollout 上，强 teacher $T$ 与同家族低能力参考模型 $R$ 都给对齐文本单位评分。两者的 log-likelihood 差 $\Delta_T=\log p_T-\log p_R$ 是**家族内的能力变化**；它消去直接师生对比中共同的家族偏移。另一边冻结初始 student 作为 $\pi_{ref}$，用当前 student 相对起点的变化 $\Delta_S$ 防止更新无节制地追逐某些 token。Compass 的 sampled advantage 由 $\Delta_T-\alpha\Delta_S$ 形成，再接原来的 on-policy 优化循环。

论文还用 MoE teacher 的两种专家激活配置，从同一权重构造强/弱 teacher 参照；这避免再保存一个完整独立 checkpoint，但会改变前向配置与调用成本。读 Figure 2 时注意**三套分布**：强 teacher、teacher 家族参考、student 自身参考；不是简单双模型 KL。原文未给作者官方训练仓库链接，引用的 EvalScope 是评测工具，不能冒充方法实现。


**图解。** 图上半区对强 teacher 与同家族弱参考求差，保留能力变化；下半区对当前 student 与冻结起点求差，限制策略偏移。右侧的 advantage 汇合两条差分。图中的文本空间对齐先于这两条计算，不能省略。 [图源：arXiv 2609.10154v1](https://arxiv.org/html/2609.10154v1)。

## 3. 实验设置与算力



| 配置 | 原文设置 | 复现口径 |
|---|---|---|
| 学生 | Granite4.1-3B、Qwen3-4B、OLMo-3-7B | 每组 OPD 与 CompassOPD 共享 cold-start checkpoint |
| 主教师 / 参考 | Qwen3.5-35B-A3B / Qwen3.5-0.8B | 二者均为 non-thinking，训练中冻结 |
| Prompt 来源 | Qwen3-4B 用 DAPO-Math；其余两者用 DeepScaleR-Preview | 不能写成所有学生共用混合数据 |
| 采样 | 温度 1.0，top-p 1.0 | prompt 上限 2,048，response 上限 24,576 |
| 优化 | AdamW，常数学习率 1×10⁻⁶，无 warmup | global batch 128，PPO mini-batch 64 |
| 微批 / 方法参数 | 每 GPU micro-batch 1；α=0.5 | 不是 SFT 阶段的学习率和批量 |
| 硬件 | 8×NVIDIA H200 | 全流程 GPU-hours 仍需单独记录 |
| 评测 | 每题独立生成 16 次取平均 | 不是从 16 条回答中挑一个答案 |

配置来源：[原文 §5.1](https://arxiv.org/pdf/2609.10154v1#page=6) 与 [附录 A.1–A.3](https://arxiv.org/pdf/2609.10154v1#page=11)。教师、家族参考和初始学生参考均冻结，只有当前学生更新。

公平对照至少要固定 student 起点、训练 prompt、生成 token 总量和评测解码。只固定 step 不够：多 rollout、更长回答和更大 teacher 会显著增加计算。若论文没有完整 GPU 型号、卡数或 GPU-hours，本报告将其视作披露缺口；复现时需单独测量 student 生成、teacher 前向、反向传播和评测四部分 wall-clock。已有正文中的论文专属模型、数据和参数说明应与这张账本结合阅读。

统计上应报告多个随机种子或置信区间，并把 checkpoint 选择放在独立验证集。Pass@k 会随 k 和采样温度上涨，不能与 greedy accuracy 混写；LLM judge 需要固定版本与 prompt；verifier 过滤后的有效样本量也要报告。只有配置、预算和指标都对齐，结果差异才可归因于方法。

训练 prompt 用 DAPO-Math、DeepScaleR-Preview；评测 AIME24/25/26、HMMT25 Feb/Nov、HMMT26、MATH500，**每题 16 次独立生成取均值**。teacher 选择 Qwen3.5、Qwen3、Mistral 多家族，student 包含 Granite 等异族模型；主要比较 SFT、普通 OPD、CompassOPD。

同样是 16 次生成，训练过程的 teacher 调用数可能比普通 OPD 多，因为要评分强/弱 teacher 与 student reference。原文主表没有统一 GPU-hours；若用于工程决策应比较额外前向是否值得精度收益。

## 4. 结果与图表解读

原表固定 Qwen3.5-35B-A3B 教师，并为 CompassOPD 使用 Qwen3.5-0.8B 参考模型。各学生区块中的 OPD 对照共享教师与训练条件，适合观察校正项的作用；跨区块则不能直接归因于方法。参考模型额外评分的成本应计入效率比较，而不只比较最终准确率。 图表源：[arXiv 2609.10154v1 PDF，第 6 页](https://arxiv.org/pdf/2609.10154v1#page=6)，仅裁图表区域。

![Table 2：Granite 学生与不同教师族](./assets/papers/paper-opd-2609-10154/table-2-results-pdf.png)

原表在 Granite4.1-3B 学生上分别使用 Qwen3 和 Mistral 教师，在每个教师组内比较 OPD 与 CompassOPD。它检验主结论是否只依赖一种教师家族，但并不覆盖任意 tokenizer 或参考模型选择。若某组收益较小，应保留为方法相容性边界，而不是只报告最大增益。 图表源：[arXiv 2609.10154v1 PDF，第 7 页](https://arxiv.org/pdf/2609.10154v1#page=7)，仅裁图表区域。

结果证据应形成闭环：主表回答“最终是否更好”，曲线回答“训练是否更稳/更快”，消融回答“哪个部件起作用”，成本表回答“是否等预算”。任一环节缺失都降低因果强度。尤其在 OPD 中，更强 teacher、更长 rollout 或更多 teacher 前向本身就可能提高分数，因此必须同时报告 teacher 调用量和生成 token。只引用平均值还会掩盖 AIME 这类小样本基准的高方差。

实践决策不能只追最高 accuracy。若目标是单次在线回答，应重视 Pass@1/Avg@k 与延迟；若允许 test-time scaling，才关注较大 k 的 Pass@k；若模型需要持续更新，还要测 OOD、遗忘和连续多轮蒸馏。本文据原图与正文只给“这些实验设置下”的结论，不把局部结果外推成普遍规律。

**Table 1** 中 Qwen3.5-35B-A3B teacher、Granite4.1-3B student 的七项平均：base **12.66**、SFT **24.39**、普通 OPD **25.36**、CompassOPD **30.86**。AIME24 普通 OPD **25.00**，Compass **33.75**；HMMT25 Feb 两者都是 **12.29**，提醒收益不是每项都有。另一个 student 分块普通 OPD **32.93**、Compass **34.74**，增益更小。师生起点与家族差异不同，效果自然不应只看一个总平均。

对比 Figure 里分解的家族偏移与能力变化，阅读重点是“减去弱参考后，哪些 token 的方向改变”。如果弱参考本身太弱或其 tokenizer 与强 teacher 仍不一致，差分会有噪声；该方法的优势并不意味着所有额外参考都值得。

## 5. 局限、结论与后续阅读

共同局限可以归为四类：teacher 可能在 student 前缀上失准；on-policy 反复调用 teacher，训练成本高于离线 SFT；tokenizer/EOS/template 不一致会把协议差异伪装成知识差异；多数论文集中在数学或可验证任务，开放式对话、代码和长期遗忘证据仍少。CompassOPD: Cross-Family On-Policy Distillation via Within-Family Likelihood Shifts 应在这些边界内理解，不能因一个平均分提升就宣称普遍优于所有蒸馏或 RL 方法。

后续复现优先做等生成 token、等 teacher 前向和等 GPU-hours 三套对照，并报告长度、熵、KL、有效 token、梯度范数、OOD 与失败案例。阅读路线可依次对照普通 off-policy KD、标准 RKL OPD、本文专属改进以及同主题的稳定化/跨 tokenizer 工作。最终判断标准是“收益来自哪里、付出什么成本、在何种条件下失效”，而不是只复述摘要。

CompassOPD 的前提是能找到有意义的同家族参考模型，并在同一文本单位上取得强/弱 teacher 的 log-prob。若只能使用黑盒文本 API，目标难直接实现。它较适合跨家族蒸馏，但多模型前向成本不可忽视。与 [MOPD-Router](#paper=paper-opd-2609-30837)连读可区分：一个消除家族偏移，一个在多位 teacher 间逐位置选择信号。
