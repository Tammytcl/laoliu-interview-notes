## 1. 背景与已有工作

通常的 OPD 让 student 先生成一条轨迹，再让 teacher 在这条轨迹的各个前缀给出 token 级监督。这比只看最终“对/错”的 verifier reward 更密，但常见实现把同一题采出的多条轨迹分别送给 teacher。对于数学和代码题，一组答案本来就包含有价值的局部对照：有的路径解对了，有的路径虽然看似合理却在某一步走错。只用每条轨迹自己的 prefix，teacher 看不到这种同题正反例。

本文的 Multi-Rollout On-Policy Distillation（MOPD）要解决的是**如何把同一 student 对同一 prompt 的多次尝试变成更可靠的 teacher 上下文**。它与 [Multi-Teacher MOPD](#paper=paper-opd-2606-30406)同用缩写，但本文核心是多 rollout 与 peer context，teacher 可以是带额外上下文的 self-teacher；另一篇核心是合并多个领域 RL teacher。

要区分两个信号层次。Verifier 把一整条答案标为成功或失败，便于把轨迹分组，却不知道哪个 token 开始犯错。Teacher 读取同题的成功/失败 peer 后，再对目标 rollout 的 token 序列打分；作者希望成功 peer 显示有效推理模式，失败 peer 暴露具有迷惑性的错误分支。

为什么不能简单把同一题的多条答案都拿来做 SFT？因为“成功答案”只告诉 student 应写成什么，不告诉它在自己已经写出某个错误前缀之后，下一 token 哪些选择比较合理。反过来，单个成功/失败的标量奖励虽然能训练策略，却很难指出具体偏离发生在哪一步。多 rollout OPD 的信息优势并非“采样更多”本身：对照方法同样生成多条 student 轨迹，差别在于是否让 teacher 在判断目标轨迹时看到同题的其他尝试。

这也限定了方法适用场景。数学题有标准答案，代码题可跑测试，工具任务可由环境返回结果，因此 verifier 能将同题尝试分组。开放式写作如果没有可靠的成功/失败定义，就没有本文默认的 peer 标签；把有噪声的人类偏好标签直接等同于程序验证结果，需要额外检验。

## 2. 方法与实现机制

给同一个 prompt $x$，student 当前策略采样 $N$ 条轨迹 $y^{(1)},\ldots,y^{(N)}$。Verifier 把它们分为成功集合 $Y^+(x)$ 与失败集合 $Y^-(x)$。对其中目标轨迹 $y^{(i)}$ 构造 teacher 上下文时，要从 peer 集里**排除目标本身**，否则 teacher 可能直接看到待评价答案。论文比较两种构造：只放一个或多个成功 peer；或同时放成功 peer 与失败 peer，使 teacher 在目标前缀上有一个可对照的“应如何做/应避开什么”上下文。

teacher 的下一 token 分布可记为 $q_\phi(\cdot\mid x,C_i(x),y^{(i)}_{<t})$；$C_i(x)$ 是从目标以外的 peer 构造的上下文。Student 仍然是在自己采出的 $y^{(i)}$ 上更新，所以“on-policy”来自 student 轨迹；teacher 额外看 peer 是 privileged supervision。论文在数学任务使用 reverse KL，在其他任务使用 Jensen–Shannon divergence。两种 divergence 的梯度性质不同，不能把实验看成只增加 peer 文本的单因素改动。

把该数据流写成教学用的统一记号，监督目标是沿 student 自己的轨迹比较两个条件分布：

$$
\mathcal L_{\text{peer}}=\mathbb E_{x,\,y^{(i)}\sim\pi_\theta}\sum_t
D\!\left(\pi_\theta(\cdot\mid x,y^{(i)}_{<t}),\;q_\phi(\cdot\mid x,C_i(x),y^{(i)}_{<t})\right).
$$

这里 $D$ 表示实验选用的散度，不把数学任务的 reverse KL 和其余任务的 JS divergence 混成同一个具体 loss。两边都评价**目标轨迹同一前缀**，但 teacher 还看到目标以外的 peer，这一额外条件就是方法区别于普通 OPD 的位置。式子是为帮助读者理解的归纳，训练器的采样、mask、权重与具体估计应以原文 §4 和固定 commit 为准。

用集合写，$Y^+(x)=\{y^{(j)}:R(x,y^{(j)})\ge\tau\}$，$Y^-(x)$ 则为低于阈值的轨迹。给目标 $i$ 构造上下文时，先从两个集合中删除 $y^{(i)}$，再按策略选主成功解、额外成功解与失败解。这里 $R$ 是 verifier，$\tau$ 是成功阈值。这个“删除自身”的操作尤其重要：若 teacher 看到了要打分的完整答案，它对前缀的概率可能只是读取答案而非理解题目，token 级监督会被信息泄漏污染。若一组 $N$ 条轨迹没有成功解，构造就不能凭空拿到正例；实现必须有回退逻辑，报告不能把所有 prompt 都想象成有完整正反 peer。

**核心源码与方法对照**

作者公开了 [MOPD 代码](https://github.com/viviable/mopd_code)。本报告静态核读 commit [`cf375056`](https://github.com/viviable/mopd_code/tree/cf375056381060b1b17c352c951089f8e944c92c)，未执行训练。训练器的 [`_maybe_build_self_distillation_batch`](https://github.com/viviable/mopd_code/blob/cf375056381060b1b17c352c951089f8e944c92c/verl/trainer/ppo/ray_trainer.py#L980)接收 rollout batch 与 reward tensor，按同一 `uid` 收集成功和失败索引，然后选择主要成功解、另一条成功解、失败解，并构造给 teacher 的消息；这对应论文的 $Y^+,Y^-$ 与 $C_i$。同文件的 [`_build_control_peers`](https://github.com/viviable/mopd_code/blob/cf375056381060b1b17c352c951089f8e944c92c/verl/trainer/ppo/ray_trainer.py#L784)用于匹配 block/token 预算的对照，避免“多看了文本”本身解释全部收益。代码继承并改造 verl/SDPO 训练器，`loss_mode` 的分支和配置里的 `self_distillation` 必须一起看；孤立复制构造上下文的函数不会产生完整的 OPD 更新。

沿代码调用链复核时，先用 `uid` 验证同题分组，再看 reward 如何把 peer 分为成功/失败，随后核对目标索引是否被排除，最后才检查构造出的消息是否传到 teacher 评分和 student loss。选择“2 成功 + 1 失败”会加长 teacher 输入，因此 `_build_control_peers` 的长度匹配对照不是附属细节，而是检验改善究竟来自信息内容还是纯粹更多 token 的关键。还有一层实现差别：teacher 可由 student 同源模型在附加 peer 条件下扮演，并不总是大一号独立专家。若把本文误读为只依赖更强外部 teacher，就会错过 self-teacher 的实用性与局限。

## 3. 实验设置与算力

实验覆盖数学、代码、科学问答和工具使用。数学训练用 DeepMath 中难度至少 6 的约 **57K** 题；评测用 AIME2024、AIME2025 与 HMMT25。代码评测用 LiveCodeBench v6 的 **131 道**竞赛题；科学问答用 SciKnowEval L3，工具使用用 ToolAlpaca。数学/代码报告 mean@8 与 pass@8；这两个指标分别看平均单次成功率和八次至少一次成功率，不应混写。

| 项目 | 原文 §5 可核配置 |
|---|---|
| Student / 对照 | 主数学比较从 Qwen3-4B 出发，对照 base、GRPO、SDPO；代码另含 Qwen3-8B。 |
| Rollout | prompt batch 32；每题训练时采样 8 条 student rollout。 |
| Peer context | 主配置通常为 2 条成功 peer + 1 条失败 peer；另有只放成功、只放失败等消融。 |
| 优化 | Actor learning rate $1\times10^{-5}$，warmup 10 steps；self-distillation mixing coefficient $\alpha=0.5$，top-$k=100$。 |
| 长度与精度 | prompt 最高 2048 token；response 最高 4096，数学 8192；bfloat16，FlashAttention-2。 |
| 系统 | verl、异步 vLLM rollout、FSDP 优化；附录 Table 9 的逐步墙钟比较在 **8×H100**、batch 32、每题 8 rollouts 上进行，但未给完整训练总 GPU-hours。 |

这些成本之外，还要计入 verifier、peer context 带来的 teacher prompt token 与多 rollout 推理开销。固定“8 条 rollout”控制了部分 student 生成预算，但不自动代表所有方法 teacher 调用成本相等。

![Table 9 · 8×H100 上的单步时间对比](./assets/papers/paper-opd-2605-12652/table-9-pdf.png)

**Table 9 解读。** 这是附录里实际披露的算力配置，纠正了先前报告“未给 GPU 型号/卡数”的遗漏：在 **8×H100** 上，LCB 单步总时间从 SDPO 的 550 秒到 MOPD 的 600 秒，QA-Chemistry 从 90 秒到 120 秒。前者约 +9.1%，后者约 +33.3%，说明 peer 条件可能增加明显开销，且不同任务的 reward 时间占比会改变总体影响。表中 Gen/Reward/Adv/Update 四列相加不等于 Total，原文解释还有数据搬运、batch 重组等未单列开销；不能用各列简单相加反推遗漏的 GPU-hours。[原表：PDF 第 21 页](https://arxiv.org/pdf/2605.12652v2#page=21)。

## 4. 结果与图表解读

![Table 1 · Qwen3-4B 数学任务的 mean@8 与 pass@8](./assets/papers/paper-opd-2605-12652/table-1-pdf.png)

**Table 1 解读。** Qwen3-4B 数学结果中，AIME2024 的 mean@8 从 base **16.89**、GRPO **17.09**、SDPO **7.29**，到 MOPD **28.54**；但 AIME2025 上 GRPO 的 mean@8 **25.80** 略高于 MOPD 的 **25.41**。同一行还要对照 pass@8：它表示八次采样至少有一次成功的比例，与 mean@8 的单次平均表现不是同一个指标。结果支持多个任务上明显受益，并非每个格子最优；SDPO 在数学上的下滑也提示“privileged self-teacher”本身并不保证成功，peer 上下文的内容重要。[原表：PDF 第 7 页](https://arxiv.org/pdf/2605.12652v2#page=7)。

![Table 4 · 正例、反例 peer 构造的消融](./assets/papers/paper-opd-2605-12652/table-4-pdf.png)

**Table 4 解读。** Science QA 化学题 mean@8 在只放 1 条成功 peer 时为 **51.90**，只放 1 条失败 peer 为 **35.67**，放 2 成功 + 1 失败为 **74.29**。LiveCodeBench 对应配置从只放 2 成功的 **55.62** 到 2 成功 + 1 失败的 **61.82**。这说明成功例子提供主要方向，而失败例子在已有成功例子的条件下补充边界信息；单独的失败例子并不充分。表末的“8 条解、2/4 小时”条件并不是简单加更多失败 peer，而涉及更长计算与上下文，不能直接把 81.25 归因于某一类 peer。组大小、teacher 上下文长度和成功轨迹可用率仍是混杂因素。[原表：PDF 第 7 页](https://arxiv.org/pdf/2605.12652v2#page=7)。

![Figure 4 · 七种 peer 上下文的六项 teacher 信号质量指标](./assets/papers/paper-opd-2605-12652/figure-4-source.png)

图源：[arXiv 2605.12652v2 LaTeX 源码](https://arxiv.org/src/2605.12652v2)，`figs/teacher_metrics_main_v2.pdf`。

**Figure 4 解读。** 六个小图依次量化排序相关、两两判断、成功样本 AUC、point-biserial 相关及 Brier 校准误差；除 Brier 越低越好，其余越高越好。作者固定候选 rollout，只改变 teacher 可见的 peer 上下文：灰条为其他条件，橙条“2 Sol. + 1 failure”在 pairwise accuracy 达约 **0.47**，高于只放第二成功解的约 **0.35**；Spearman 相关也从近零提高到约 **0.16**。然而 Brier 上橙条并非最优，说明排序更准不等于概率校准也最好。它提供“teacher 信号更可靠”的机制证据，仍须与最终 benchmark 和 Table 9 的调用时间一起看。[原图：PDF 第 8 页](https://arxiv.org/pdf/2605.12652v2#page=8)。

## 5. 局限、结论与后续阅读

这篇论文最适合用于**同一题本来就采多条答案且有可靠 verifier**的场景。若成功轨迹极少，peer 构造可能没有正向锚点；若 verifier 有误，失败/成功标注会把错误引入 teacher 上下文。代码里的长度匹配对照说明作者也意识到“更多上下文”是替代解释，需要将信息内容与 token 预算分离。

本文提供的证据支持 peer-conditioned teacher 在所测数学、代码、科学 QA 与工具任务上改善若干指标；没有给出任意开放生成任务上同样有效的保证。下次复现宜固定 student rollout 集，分别移除成功/失败 peer，并报告 teacher token 开销、有效 peer 比例和完整 GPU-hours。作者 Table 9 已披露单步 8×H100 时间，但不足以还原所有训练阶段的总成本；Figure 4 的信号提升与 Table 4 的最终任务改进也不是同一指标。
