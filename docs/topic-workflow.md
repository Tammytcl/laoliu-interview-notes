# 专题整理工作流 v1

样稿：[训推框架梳理](../content/questions/systems/training-inference-frameworks.md)。这一流程用于基础知识、工具 / 框架比较和面试练习，沿用本站 Markdown 问题笔记的格式；单篇论文精读仍遵循 paper-workflow.md。模板：[topic.md](../templates/topic.md)。

## 1. 定义交付与整理边界

先明确读者基础、主问题、需要比较的对象、内容所在分类、是否替换旧文和是否发布。把交付写成读者能完成的动作，例如“比较 slime / verl、说明同一训练任务如何接入不同框架”。不要先收集几十个项目再决定文章主线。

清理旧文章时先检查工作区，将旧内容移出 `content/questions/` 到 `archive/`，记录替代 ID，更新站内链接与 paper `note_ids`。`content/metadata/note-redirects.json` 保留旧 URL 到新文章的映射；归档不进入网页列表。修改前核对已有用户改动，不能覆盖未提交工作。

## 2. 调研与来源分级

按“官方仓库 / 文档 → 原论文 → 作者博客 → 社区经验 / 面经”顺序检索。每个对象至少回答所在层、职责、输入输出、关键设计、版本支持、边界、源码阅读路线。比较使用同一组维度，不按项目广告词逐个介绍。

社区博客可以提供问题线索与实践叙述，技术结论回到作者资料核对。面经区分已核实的个人记录、社区题库主题与本文延伸；不把整理题标成公司真题，不根据题库数量推导出现概率，不复制外部答案作为正文。

正文中在关键结论附近放链接，末尾提供带用途的来源表。在 `content/research/<topic>-sources.json` 登记唯一 source ID、title、url、kind、purpose、reviewedAt。代码来源必须固定 `revision` 与 `pinnedUrl`；需要监控的文档增加 `watchUrl` 与人工已核版本的 `reviewedSha256`。查不到的实验版本明确说明，不能编造。

固定版本是核对基线，不保证上游当前仍兼容。发布前核对全部关键能力的当前版本；正文明确日期与已知限制。性能数字必须带模型、硬件、版本、精度、长度、负载、基线和指标，不把作者 benchmark 改写为本人复现。

## 3. 组织正文：知识解释与问答互相支撑

先确定一篇的主问题，再选择必要模块。框架专题按“定位 → 使用入口 → 同层对比 → 同一任务的接入差异 → 选型问答 → 来源”组织。初学者应能在第一次出现术语时知道含义。每个重点问题包括直答、机制、例子和边界；常见误解融入对应问题，不堆成免责声明。

基础知识只解释到足以理解当前区别，不默认加入显存推导、通信、推理优化、系统设计和通用题库。选型是约束下的推断，和官方支持、作者测量、本次实测分开。面试提纲保留稳定题号，提供回答要点与可继续追问的问题；跨专题重复知识尽量链接到主文。

## 4. 插图与证据

有合适作者图时优先用架构 / 数据流 / 概念图，下载到 `assets/<topic>/`，逐张查看后再引用。每张登记 origin、sourcePage、credit、retrievedAt、sha256、visuallyVerified、role 与 explanation。作者归属保留在图旁；本地保存用于避免失效热链，不表示获得新的许可，图片继续遵循原来源条款。

逐图解释节点、箭头、含义与不能推出的结论。历史图需要注明历史时间；展示卡数不是推荐配比，概念图不是实测证据。新绘概念图明确标成本文示意。小图和宽表分别检查桌面 / 手机，不拉伸图像、不裁掉正文。

## 5. 迭代检查与发布

先内容审阅：逐条回查关键结论、公式、示例、选型和题目归类；明确疑点再修订。机械检查通过不能替代事实核查。新增专题在 `content/research/topics.json` 注册 id、sources、figures、requiredSections 与必要的题目约束。

```bash
npm run topics:quality
npm test
npm run build
npm run test:browser
```

构建也会执行专题检查，防止跳过 CI。专题检查验证来源登记、固定版本、图片文件与哈希、公式渲染、必要模块、题号和站内链接。改过读者 UI 或路由时做浏览器验收，正文新增宽表 / 插图也需检查手机布局。

交付前 `git diff --check`，检查最终 diff，只提交本次变更。若用户已授权推送与网页更新，就提交并 push；否则先交付可评审改动。推送触发现有 Pages workflow，确认构建 / 部署结果，再运行线上验收。不能仅以 push 成功声称网站已更新。

```bash
npm run topics:check-live -- https://tammytcl.github.io/laoliu-interview-notes/
```

当前线上检查针对训推框架样稿，覆盖 Infra 列表、旧链接跳转、当前正文与问答、两张架构图、目录定位和手机布局。扩展到新专题时添加相应读者流程。

## 6. 持续更新与自动化边界

现有 GitHub Actions 每周一 UTC 02:17（北京时间 10:17）运行 `topics:watch`，观察已登记的核心仓库和文档，提交来源观察快照与候选变化账本，检查并重新部署网页。也可以 workflow_dispatch 或本地手动执行：

```bash
npm run topics:watch
```

`reviewedAt / revision / reviewedSha256` 是**正文已核对基线**；`<topic>-observations.json` 是**自动观察状态**。检测程序不会更新前者。候选变化保持在 `<topic>-pending.md`，仓库提交可能只涉及与文章无关的代码，不应自动当成结论过时。抓取失败保留上次成功值与 pending 状态，报告失败原因，不将失败当作无变化。

发现变化后，人或后续整理 Agent 读取 compare diff，定位正文、例子、原图与题目受影响处；完成核查和修订后更新基线，再经过质量检查与发布。该流程自动完成发现、记录、检查、推送与部署；语义重写需要读取新资料，本仓库目前没有配置定时 LLM 写作服务。

来源清单、候选记录、模板和本文流程可从文章末尾下载。未登记监控的网页依靠下一次调研核查；不宣称监控了整个互联网。继续整理时可以给 Agent 以下任务：

> 按 docs/topic-workflow.md 整理指定专题。先读样稿与来源观察账本，核对当前官方资料与作者解释，围绕本轮主问题写区别、使用、选型与相关问答；外围主题记录到后续范围；逐图查看，登记来源与版本；至少两轮内容审阅，完成检查。已授权推送时提交、推送并验证线上网页，报告实测范围与待核问题。

## 8. 本轮范围约束

根据用户修正，样稿聚焦不同训练框架的区别与使用。每段内容应直接回答“负责什么、怎么接、改哪里、怎么选”之一。问答围绕框架组织，数量不设硬门槛；不为了凑章节或题目数扩大范围。旧版大范围稿和来源清单在 `archive/topics/2026-10-03/` 保存，后续按显存、并行通信、推理优化、RL 系统排障等各自的主问题逐轮处理，本轮不展开。

本次重写后，来源清单与监控也只保留直接相关的框架资料；阅读路线和验收依据正文内容更新，不要求延续旧版 60 题与三张图。
